# Milwaukee Tool 工作汇报格式规范

为 Milwaukee Tool 内部汇报类 PPT 定义**统一格式**，并附带生成器：带 Layout 标记的 md 文稿 → Milwaukee 格式 pptx（全部原生可编辑）。

---

## ⚠️ 适用范围：两层规则，先判断走哪条

本 skill 的规则分两类，动手前先判断当前任务属于哪种：

### A. 始终生效（所有 Milwaukee 汇报 PPT 都要守）

- **标题三层结构**（§4）：主标题（话题）+ 副标题（action title）+ 正文 lead（结论 + 数据）
- **每节一个核心信息**（§7）：一节只回答一个问题，超出就拆
- **页面布局规则**（§5：Cover + Body 布局，banner / logo / 页脚）
- **设计系统**（§6：品牌锚点、色板、红色纪律）
- **内容硬约束 / 禁用元素**（§7）

### B. 仅项目汇报模式生效（`report: project`）

以文稿 frontmatter 的 `report: project` 为准：写了就是项目汇报模式，套用 B 类规则；没写就**跳过** B 类规则。
只有用户**明确说"这是一个项目的完整汇报"**时才开项目汇报模式（整理文稿时写上 `report: project`）；拿不准就问用户，不自行开。

项目汇报模式套用下列三条：

1. **固定 Agenda 顺序**（§1）：8 节按规定顺序，可加子节点，不可改顺序、不可去节
2. **PDCA 标注**（§2）：每节标注 `P` / `D` / `C` / `A` 图标——文稿里每页写一行 `PDCA: <字母>`，生成器在 banner 下沿与正文区上沿之间（1.02–1.30"）的右侧窄带插 `assets/pdca/` 的图标
3. **"已落地 vs 未来" 严格分离**（§3）：整篇不写未来规划 / Next Step / Roadmap / 画饼（月报底部"下一步计划"为唯一例外）

> **判断示例**
>
> - "这是项目 X 的完整汇报，帮我做 PPT" → 走 A + B（写 `report: project`）
> - "帮我做项目 X 的汇报 PPT"（没说是完整汇报） → 先问用户是不是完整的项目汇报，是才写 `report: project`
> - "做这个月的月报" → **只走 A**（月报模式，不写 `report: project`）
> - "把这次展会参观做成汇报 PPT" → **只走 A**（不强制 Agenda/PDCA，可自由组织章节，可写"后续建议/Next Step"）
> - "做个培训分享 PPT" → **只走 A**

非项目汇报场景（展会汇报、培训、分享、综述等）**鼓励**按内容自然组织章节，并且**允许写后续建议 / 行动项 / Next Step** —— §3 的"不写未来"约束此时不生效。

## 生成 pptx

生成器在 `scripts/generate_ppt.py`（本节路径都相对本 skill 目录），只依赖 python-pptx（装了 Pillow 时多图宽度按比例分），默认用 `assets/MS_Template.pptx`：

```bash
python3 scripts/generate_ppt.py <文稿.md> [-o 输出.pptx]
```

用户要出 pptx 时按这四步走：

1. **整理文稿**：把用户的自由文稿整理成带 Layout 标记的 md——每个 `#` 一页，`##` 是 action title，一行 `Layout: <版式名>` 选版式（不写 = evidence），普通文字行是本页一句话结论，`Next:` 是下一步（月报模式两句都进底部红条；通用模式和项目汇报模式下结论画成标题下的 lead、`Next:` 画在页底一行，见 §5 Page 2）。版式字段、选版依据、反例都在 `references/layouts.md`，整理前先读；内容仍守本文件 §4、§6、§7（项目汇报再加 §1–§3）。完整示例：`examples/demo/deck.md`。
   - 用户没有提供图片时，不选 `evidence` / `image-text`（这两种必须配图），`before-after` 两侧都写短文；和 ppt-grill「素材清单为"无"」的规则一致。
   - 用户先用 ppt-grill 定过**简报**（`简报.md`）时，简报就是这一步的唯一输入：按 ppt-grill「交给 milwaukee-ppt」一节的对照表逐行转成 md，放在简报同目录，页数、页序、标题、数字和简报逐项一致。用户还没定简报、但想先把结论和页序磨清楚时，先走 ppt-grill。
2. **生成**：跑上面的命令。退出码非 0 = 文稿有错，按错误信息里的「页「标题」」改 md 再跑；`警告:` 行不中止，带进第 3 步一起处理。
3. **审核**：走 ppt-review skill——跑审核脚本、照它的核对清单逐页判断、改 md 重新生成，最多两轮。审核脚本单独跑的写法：

   ```bash
   python3 scripts/review_deck.py <文稿.md> <输出.pptx>
   ```

   每条问题一行 `[规则] 位置：问题 → 怎么改`，全过打印 `REVIEW OK`；规则全表见 `scripts/README.md`「审核命令」。转 PNG 看图降为可选复核（能读图时用）：`soffice --headless --convert-to pdf --outdir <目录> <输出.pptx>`，再 `pdftoppm -png -r 80 <输出.pdf> page`。
4. **交付**：按 ppt-review「交付给人」把 pptx 连同最后一轮审核结果、未解决项交给用户；用户还要改某页细节时，按下面「生成后细调」做。

文稿格式：

- frontmatter 写 `title` = 通用模式：封面主标题 title，副标题由 `subtitle` 和「`date`   `author`」两行组成；写了 `closing` 才加收尾页。
- frontmatter 不写 title、写 `month: YYYY-MM` + `author` = 月报模式：封面「<Mon>. YYYY Working Summary」、结尾 Thank You，与月报模式约定一致。
- frontmatter 加 `report: project` = 项目汇报模式（B 类规则，见「适用范围」）：各页可写 `PDCA: P|D|C|A`（组合用 `/`，如 `PDCA: D/C`，不区分大小写），生成器在该页 banner 下沿与正文区上沿之间（1.02–1.30"）的右侧窄带插对应 PDCA 图标；不写 `PDCA:` 的页没有图标。没写 `report: project` 却写了 `PDCA:`、字母写错或重复、`report` 写成 project 以外的值都报错。生成器不检查章节顺序和各节 PDCA 是否齐全，交给审核 `review_deck.py`：章节乱序、缺节、缺 PDCA、团队页带 PDCA、PDCA 和所属节不符（含 06 节一页标了 `D/C`）都会报出来。
- 页面通用字段：`Tag:`（正文区右上角月份标识）、`PDCA:`（项目汇报模式）、`Next:` / `下一步：`；所有版式都支持。

| `Layout:` | 用途 | 模板 layout | 字段 |
| --- | --- | --- | --- |
| `evidence`（默认） | 截图 / 实物证据 + 结论（lead；月报为底部红条） | 0 | 0–3 张图 |
| `before-after` | 改前改后对比 | 3 | `### Before` / `### After`（各一张图或一段短文 + `Caption:`）+ 结论（lead；月报进底部红条，第一个 `###` 前可另写一句 lead） |
| `process` | 3–5 步流程 | 4 | `1. 步骤名 \| 一句说明` |
| `stats` | 2–4 个结果数字，分栏，每个数字带解读 | 5 | `- 标签 \| 数字 \| 一句说明`，最多一条 `- !…` 标红；下面缩进的 `- ` 是解读（每张 ≤3 条）；可选一行 `口径：` |
| `stats-side` | 左边 2–3 个数字、右边编号结论 | 5 | 卡片写法同 stats（不带解读）+ 可选 `### 小标题` + 1–4 条 `> 结论要点` + 可选 `口径：` |
| `timeline` | 3–6 个时间节点，可按状态着色 | 6 | `- [!]日期 \| 标题 \| 说明 [\| 状态]`，`!` = 关键里程碑；状态全写或全不写，不写为黑白灰 |
| `timeline-phase` | 3–6 个阶段的箭头阶段条 | 6 | `- [!]日期 \| 标题 \| 说明 \| 状态`，每条必须写状态 |
| `image-text` | 左图右文 | 7 | 一张图 + ≤5 条 `- 要点` |
| `section` | 隔断页（章节过渡） | 0 | 一行 `编号 \| 中文名 \| 英文名`；不放结论（不画 lead / 红条） |
| `agenda` | Agenda 目录页（列出各章节） | 0 | 3–8 行 `编号 \| 中文名 \| 英文名`（写法同 section，编号不重复）；不放结论（不画 lead / 红条） |
| `team` | 团队页（成员、角色、分工；不带头像） | 0 | 2–8 行 `- 姓名 \| 角色 \| 职责`（职责 ≤3 行）；其余文字行是分工结论（lead；月报进底部红条） |
| `table` | 表格页（同一组对象的多维对比，原生 pptx 表格） | 0 | md 管道表格，第一行是表头；2–6 列、表头以外 2–8 行，每格 ≤2 行；最多一行第一格写 `!` 强调（加粗 + 左侧红竖条）；其余文字行是结论（lead；月报进底部红条） |

生成器不做的事：Agenda 顺序（agenda 页按文稿写的顺序画，不检查是否符合 §1 的 8 节）、各节 PDCA 是否写齐、上表以外的版式（Agenda 八宫格等）；agenda 和 section 各写各的，生成器不从 agenda 自动生成隔断页、不校验两者是否一致，也不高亮当前章节；团队页不放头像、不标重点成员、不画组织架构（上下级连线）；表格页不合并单元格、不按列设宽度或对齐、不给单元格单独上色，不自动拆页（超出容量直接报错）。这些在生成后的 pptx 里按 §1–§2、§6 和 `references/layout-patterns.md` 手工补。

### 生成后细调

生成器搭骨架：品牌、版式结构、间距、颜色规则都由它固定。用户在对话里要改某页细节（节点再大一点、多加一条标注）时，直接改生成好的 pptx：

1. **检查**：`python3 scripts/inspect_ppt.py <输出.pptx>`。每页一个标题行 `== 第 N 页 | layout: <模板 layout> | 版式: <生成器版式>`，下面每个形状一行：名字、类型（占位框带 `idx=N`）、位置和大小（英寸）、文字开头。对照 `references/layouts.md`「形状命名约定」找到要改的元素。
2. **按名修改**：用 python-pptx 打开成稿，按页码取页、按 `shape.name` 取形状，改完另存为新文件。最小示例（`<skill>` 换成本 skill 目录，在成稿所在目录运行）：

   ```python
   import sys; sys.path.insert(0, "<skill>/scripts")
   from pptx import Presentation
   from pptx.enum.shapes import MSO_SHAPE
   from pptx.util import Inches
   from layouts.common import strip_theme_style
   prs = Presentation("deck.pptx")
   slide = prs.slides[2 - 1]                                   # inspect 的「第 2 页」
   shape = next(sh for sh in slide.shapes if sh.name == "Stat Number 2")
   shape.text_frame.paragraphs[0].runs[0].text = "98"          # 改 run.text，字体字号保留
   shape.top += Inches(0.1)                                    # 位置、大小用 Inches()
   note = slide.shapes.add_shape(MSO_SHAPE.RECTANGLE, Inches(9), Inches(1.4), Inches(2), Inches(0.3))
   note.name = "Note 1"; strip_theme_style(note)               # 新形状起名、去主题样式，颜色显式给
   prs.save("deck-fine-tuned.pptx")                            # 另存新文件，不覆盖原稿
   ```

   - 改文字只改 `run.text`。直接赋值 `text_frame.text` 会把段落重建成一个没有字体、字号、颜色的 run，品牌样式全丢。
   - 占位框（标题 idx 0、action title idx 10）用 `slide.placeholders[idx]` 取，idx 看 inspect 输出。
   - 新加的形状颜色显式给（`fill.solid()` + `fill.fore_color.rgb`），仍守 §6。

3. **转 PNG 确认**：命令同上面第 3 步的看图，看改过的页：没越界、没压 banner 和页脚、红色纪律没破。
4. **再审**（可选）：对细调稿跑 `review_deck.py <文稿.md> <细调稿.pptx>`。审核按当前 md 重新渲染一份、逐页比较正文形状的名字：只挪位置、改大小、改字号或改 run 文字不报；新加了形状（如示例的 `Note 1`）或删了形状，会报「正文形状被改过」——这是细调的预期结果，不用回 md 改，交付时向用户说明是哪几个形状。几何、红色面积等其他规则照常看。
5. **确认**：告诉用户改了哪些形状，并提醒下面这条覆盖规则。

改哪里：

- **回 md 改、重新生成**：内容——文字、数字、条目增删、状态、`!` 重点，以及版式选择、页的增删和顺序。
- **直接改成稿**：md 表达不了的个别调整——某个形状的位置、大小、强调（字号、加粗），加一个标注。

**重新生成会覆盖细调**：生成器从 md 整份重建 pptx，成稿上的手工改动全部丢失。细调之后用户又要改内容时，先说明这一点，由用户选：重新生成后再细调一遍，或者内容也直接在成稿上改。

## 1. 固定 Agenda 顺序（不可改、不可去节）

> ⚠️ **本节属于 B 类规则，仅项目汇报模式（`report: project`）生效。** 展会汇报、培训分享等场景跳过本节，按内容自然组织章节。

| #   | 章节               | 英文(固定)   | PDCA         | 这一节要回答什么                                                 |
| --- | ------------------ | ------------ | ------------ | ---------------------------------------------------------------- |
| 01  | 项目背景           | `BACKGROUND` | `[PLAN]`     | 为什么做、痛点是什么                                             |
| 02  | 项目目标           | `TARGET`     | `[PLAN]`     | 目标是什么、要解决什么                                           |
| 03  | 项目范围           | `SCOPE`      | `[PLAN]`     | 边界，包含什么、不包含什么                                       |
| 04  | 项目应用场景       | `USE CASES`  | `[PLAN]`     | 在哪些场景落地                                                   |
| 05  | 项目节点           | `MILESTONE`  | `[DO]`       | 时间线、关键 milestone                                           |
| 06  | 项目行动与成果     | `OUTCOMES`   | `[DO/CHECK]` | **已完成的工作**和**已拿到的结果** —— 禁止写"将要 / 计划 / 未来" |
| 07  | 项目团队           | `TEAM`       | —            | 谁参与、分工（生成器版式 `team`）                                 |
| 08  | 持续优化与经验沉淀 | `LESSONS`    | `[ACT]`      | **上线后已落地的迭代**和经验沉淀 —— 禁止写未来 roadmap           |

**英文标题为强制项,不可改写**(例如不能把 `TARGET` 改成 `OBJECTIVES`、`MILESTONE` 改成 `TIMELINE`、`USE CASES` 改成 `SCENARIOS`)。
统一英文有两个作用:(1) 跨项目汇报视觉一致;(2) 听众扫一眼英文就知道这是 Agenda 第几节,不需要重新理解。

子节点英文标题自由(例如 06.2 可以叫 `GATEWAY` 或 `MIGRATION`),只要从属于父节即可。

可加子节点（如 `06.1 报表上线明细`、`06.2 用户反馈`），但：

- 不可改 8 节顺序
- 不可删除任意一节
- 子节点必须从属于父节，不可独立成章

## 2. PDCA 思维 — 每节都要标注阶段

> ⚠️ **本节属于 B 类规则，仅项目汇报模式（`report: project`）生效。** 其他场景不加 PDCA 图标。

**位置固定**：PDCA 标签放在**banner 下沿与正文区上沿之间（1.02–1.30"）的右侧窄带**（右缘贴正文区右缘），不要写进红 banner 的副标题里。
生成器写法：该页写一行 `PDCA: D`（组合 `PDCA: D/C` 按写的顺序从左到右排）。图标 0.28" 见方，放在 banner 下沿和正文区上沿之间（1.02–1.30"），右缘贴正文区右缘，不压任何版式的内容；同页写了 `Tag:` 时月份标识让到图标左侧、与图标纵向居中对齐。
标签值固定为 `P` / `D` / `C` / `A`，与上表对应。两个特例：

- 第 06 节标注 `[DO/CHECK]`：讲"做了什么"的页用 `D` 图标，讲"结果验证 / 数据核对"的页用 `C` 图标，一页只放一个
- 第 07 节"项目团队"不带 PDCA 标签

### 图标资源（直接复用，不必另画）

本 skill 已包含设计好的 PDCA 圆环图标 (`assets/pdca/{P|D|C|A}_icon.svg`，以及预转好的同名 `.png`；生成器只插 PNG，转换命令见 `scripts/README.md`)：

- 4 段圆弧组成完整循环, **当前阶段那一段红色 `#DB011C`, 其余三段灰色 `#E5E5E5`**
- 中心字母红色 Arial Black, 字号 32pt

## 3. "已落地 vs 未来" 严格分离 — 强制规则

> ⚠️ **本节属于 B 类规则，仅项目汇报模式（`report: project`）生效。** 展会汇报、培训分享等场景**允许**写后续建议 / 行动项 / Next Step。

这是用户明确的强制规则（项目汇报场景下），违反会被驳回。

- **第 06 节"项目行动与成果"** = 已完成的工作 + 已拿到的结果
- **第 08 节"持续优化与经验沉淀"** = 上线后已落地的迭代和经验
- **整篇汇报不写**：未来规划 / Next Step / Roadmap / "下一步要做什么" / 画饼

### 自检清单（写完每节扫一遍）

- [ ] 这一节有没有出现"将要"、"计划"、"未来"、"下一步"、"roadmap"？
- [ ] 第 06 节里所有动词是不是都是已完成态？
- [ ] 第 08 节里所有迭代是不是**上线后已经做过**的？

任一项答"否"，回去改。

### 月报例外（仅 §5 Page 3 适用）

月报底部允许出现"下一步计划"，但必须满足：

- 已经确定、有 owner、有时间节点的动作
- 不是空泛 roadmap、不是"探索方向"、不是"考虑做"

不满足上述条件就不要写。

## 4. 标题三层结构

中文工作汇报习惯目录式标题（"项目背景"、"项目节点"），但目录式标题不承担论证。采用**话题主标题 + action title 副标题 + 正文 lead 强化**的三层结构。

### 转换示例

| 主标题（话题）            | 副标题（action title）         | 正文 lead（章节大标题）                       |
| ------------------------- | ------------------------------ | --------------------------------------------- |
| `项目背景 / BACKGROUND`   | `报表分散已成为扩展瓶颈`       | `报表分散管理已成为扩展瓶颈`                  |
| `项目目标 / TARGET`       | `项目按目标全面交付`           | `项目按目标全面交付`                          |
| `关键数据 / KEY OUTCOMES` | `20+ 报表,9 个月稳定运行`      | `项目按目标全面交付`                          |
| `项目节点 / MILESTONE`    | `软件如期,硬件延后 1.5–2 个月` | `软件如期上线,硬件因 RFQ 流程延后 1.5–2 个月` |

### 写法约束

- 主标题：≤ 14 中文 / 28 英文字符，禁止换行；优先中英双语（`项目背景 / BACKGROUND`）
- 副标题：≤ 40 字符，必须是 action title（给结论或动作，不是话题）
- 正文 lead：重申结论 + 加数据支撑

### 验收

只读副标题序列，能不能拼出完整故事？不能就回去改副标题。

## 5. 页面布局规则

模板文件：`assets/MS_Template.pptx`（顶部红 banner + 左上 logo + 底部页脚）。

### 5.0 模板占位框契约（生成 pptx 时必须遵守）

> ⚠️ **用 `MS_Template.pptx` 生成或手工改 pptx 时，主标题 / 副标题必须填进模板已有的占位框（placeholder），禁止为它们另建 text box。** 另建文本框会导致位置飘、与 banner 不对齐、跨页不一致——这正是本节要杜绝的问题。`scripts/generate_ppt.py` 已按本契约填充；下表也是自己写代码生成时的依据。

模板 16:9（13.33″ × 7.5″）。红 banner（顶部 0–1.0″ 全宽 `#DB011C`）、左上 logo、底部页脚都在 **母版** 里，生成时不用画、不要动。8 个版式各自的占位框如下（`idx` = `slide.placeholders[idx]` 的键，位置单位：英寸）：

| 版式 index | 版式名 | 用途 | 占位框（idx → 角色，位置 L/T/W/H） |
| --- | --- | --- | --- |
| 1 | `Title Slide` | 封面 | `0` 主标题（居中，1.0 / 4.83 / 11.33 / 0.5）；`1` 副标题（2.0 / 5.42 / 9.33 / 0.5） |
| 0 | `Blank  Slide` | 正文页（默认） | `0` 主标题（banner 右上，5.08 / 0.1 / 8.25 / 0.4）；`10` 副标题（紧贴主标题下，5.08 / 0.5 / 8.25 / 0.42） |
| 2 | `Blank  Slide WITH BULLETS` | 带正文框的正文页 | 同上两个 + `1` 大正文框（0.56 / 1.42 / 12.44 / 5.75） |
| 3 | `Before / After` | 双框对比页 | `0/10` 沿用正文页；`11/12` 左右标题（2.035 / 1.96、8.395 / 1.96，2.90 × 0.43）、`13/14` BODY 内容区（0.78 / 2.78、7.14 / 2.78，5.41 × 2.91，在对比框内）、`15/16` caption 一句话、一行（0.56 / 6.12、6.92 / 6.12，5.85 × 0.35，框下）；有底部红条（月报）或页底 Next 行（通用 / 项目模式）时生成器把 caption 挪进对比框底部，详见 `references/before-after.md` |

| 5 | `Stats` | 数据对比页 | `0/10` 沿用正文页；`18` 数据区（0.56 / 1.30 / 12.21 / 4.30） |

| 7 | `Image + Text` | 左图右文页 | `0/10` 沿用正文页；`20` 图框 16:9（0.56 / 1.30 / 7.64 / 4.30）、`21` 文字区（8.50 / 1.30 / 4.27 / 4.30） |

layout 4–7 的槽位只是定位用的 BODY 占位框：生成器在槽位矩形内画原生形状，画完删掉空槽位。按 `idx` 找槽位，不按名字找（落到页面上名字会变成 "Text Placeholder N"）。

**填充规则（生成时照做）**：

```python
from pptx import Presentation
prs = Presentation('assets/MS_Template.pptx')

# 正文页：从「Blank Slide」版式新建，只填占位框，不新建标题/副标题文本框
slide = prs.slides.add_slide(prs.slide_layouts[0])
slide.placeholders[0].text = '项目背景 / BACKGROUND'    # 主标题（banner 右上）
slide.placeholders[10].text = '报表分散已成为扩展瓶颈'   # 副标题（紧贴主标题下方）
# PDCA 图标、正文 lead、正文内容 → 在 banner 以下的正文区自行排布
```

- 主标题（§4 第一层）→ 永远填 `placeholders[0]`
- 副标题 action title（§4 第二层）→ 正文页填 `placeholders[10]`、封面填 `placeholders[1]`
- 找不到某个 idx 时按 `placeholder_format.type` 兜底定位（TITLE / CENTER_TITLE = 主标题，SUBTITLE / BODY = 副标题），**仍然不要新建文本框**
- 正文 lead、PDCA 图标、正文内容不属于占位框，照 §2/§4/§6 在正文区自行排布

### Page 1 — Cover（封面）

- 项目级标题 + 副标题（不是章节标题）
- 不出现任何章节内容
- 汇报人 / 团队 / 日期 一行说明

### Page 2 — Body（正文页 · 默认布局）

只允许出现这几个元素：

- **顶部红色 banner**
- **左上**（banner 内）：Milwaukee logo
- **右上**（banner 内）：本页主标题 + 副标题
- **banner 下沿与正文区上沿之间（1.02–1.30"）的右侧窄带**：PDCA 小图标（见 §2）
- **标题下、正文区顶部**：lead —— 本页一句话结论（md 里的普通文字行），黑色粗体 22pt，左侧一条品牌红短竖线；读序是「banner 标题 → lead → 证据」。lead 是结论句，不和副标题（action title）重复
- **正文区中部**：正文内容（在 lead 以下排布）
- **页底一行**（可选）：`Next:` 下一步，黑色粗体，上方一条细线
- 底部模板自带页脚

通用模式和项目汇报模式的正文页都按本节画，**不画底部红条**；底部红条只属于月报（Page 3）。

### Page 3 — Monthly Body（月报正文页 · 实战定型）

月报每页 = **一个工作项的证据展示**：

- **banner**：主标题 = 本月主题线（如某体系建设），副标题 = 本页具体子项
- **正文区**：以截图 / 实物证据为主体（系统界面、文档、表格），少量说明文字
- **底部红条**（每页必有）：`✔ 已完成结论一句` + `Next: 下一步`（Next 受 §3 月报例外约束 —— 必须是已确定、有 owner、有时间的动作）

月报因每页底部红条，红色面积天然高于 §6.3 配额 —— **月报场景豁免面积配额**，但红条只承载"结论 + Next"，不做装饰。

### Before / After 布局（用于 §06 成果展示）

- 使用模板新增 layout index `3`（`Before / After`）；制作对应事实对比页前，读取 `references/before-after.md` 的 slot 契约、事实对应与重渲验收。

- 左 BEFORE / 右 AFTER 对置，中间是模板自带的灰色箭头；每侧框下一句 caption，保持一行
- 结论 / Next 和其他页一样：通用 / 项目模式下结论是标题下的 lead（只有这一句 lead，第一个 `###` 前不再另写文字）、Next 在页底一行；月报模式进底部红条。有红条或页底 Next 行时 caption 挪进对比框底部（月报下框底边被红条盖住约 0.04″，正常）
- lead 竖线 / 红条以外，红色只用在 AFTER 标题，**BEFORE 不用红**

## 6. 设计系统（红 + 黑白灰体系）

> **分工**：通用视觉判断（对齐 / 对比 / 重复 / 亲密性、字体搭配、字号层级）交给 **ppt-design-principles** skill。本节只管 Milwaukee 品牌专属规则：品牌锚点、色板、红色纪律。

### 6.1 不可变的品牌锚点（硬约束）

Milwaukee 品牌的硬约束**只有三项,仅限顶部 banner 区域**:

1. **顶部红色 banner** —— Milwaukee Red `#DB011C`,使用模板原样,不可改色不可缩减高度
2. **左上 Milwaukee logo** —— 白色版本,位于 banner 左上
3. **banner 内文字白色** —— 主标题 + 副标题(中英双语),不可改成其他颜色

banner 以下的正文区用色遵循 §6.2 色板。

### 6.2 色板（唯一基准 · 已落地验证）

| 角色              | hex       | 主要用途                                                               |
| ----------------- | --------- | ---------------------------------------------------------------------- |
| **Milwaukee Red** | `#DB011C` | 唯一品牌色:banner、关键数字、AFTER 强调、PDCA 红段、章节锚点条         |
| **深灰文字**      | `#1A1A1A` | 正文 lead、卡片主标题、icon row 标题、深灰大数字(与红字并列时)         |
| **中灰副信息**    | `#6B6B6B` | 描述句、副信息、注脚、来源标识、占位框元信息                           |
| **次重要灰**      | `#333333` | P1 优先级徽章底、次级标识                                              |
| **轻次要灰**      | `#777777` | P2 优先级徽章底、Cover 字段标签、tagline                               |
| **细分割线**      | `#E5E5E5` | 卡片描边、分割线、时间线主线                                           |
| **占位底灰**      | `#F5F5F5` | 图片占位框背景、BEFORE 卡片背景、灰阶强调底                            |
| **占位边框**      | `#D0D0D0` | 图片占位框描边、内嵌截图框                                             |
| **深海军蓝**      | `#1A2B5C` | 唯一冷色辅助:经验沉淀小标、安全/合规标识、"流程 / 数据"等冷概念        |
| **白**            | `#FFFFFF` | 卡片底、内嵌截图框底、banner 内文字、AFTER 卡片底                      |

简化记忆为 **"红 + 黑(深灰) + 白 + 4 档灰阶 + 1 个冷色辅助"**。
绝大多数页面只需要 `#DB011C` / `#1A1A1A` / `#6B6B6B` / `#E5E5E5` / `#FFFFFF` 这五个色。

**可选扩展色**（默认不用，启用前过下面的撞色判断）：深酒红 `#8B1E2C` / 浅红粉 `#FCE6E8`（红家族二级强调）、深松绿 `#1F3A2E` / 深石板灰 `#2D3B4E`（冷概念备用）、深橙 `#C9701F`（工业暖辅助，慎用）。

#### 撞色判断（引入任何新色前过 3 问，任一不过就换色）

1. **明度差够吗?** 红是中明度,候选色应明显更暗(深冷色)或更亮(浅灰白)。中明度的蓝/紫/绿一定撞。
2. **是不是暖系或暗冷?** 暖红 + 暖灰 = 协调;暖红 + 中明度冷色 = 撞。冷色要够暗才能上。
3. **灰度复印后还能看出层级吗?** 看不出 = 文字读不清,换色。

#### 必须避免

- ❌ **中明度纯蓝**(`#2B5BB5`、`#1E90FF` 等)、**亮绿、亮紫、亮粉、青绿** —— 与暖红撞色或显轻浮
- ❌ **渐变填充 / 阴影 / 发光 / 毛玻璃** —— Milwaukee 工业品牌一向 flat
- ❌ **三种或以上强色相** —— 保持"灰阶 + 1~2 个强色"

### 6.3 红色纪律

> **红色 = "这件已搞定" 或 "这件最危险",二选一。除此之外全交给黑白灰。**
> 红色永远在做"选择",不做"平铺"。

**语义**（红色标什么）：

| 页面性质                | 红色标注对象             | 实战做法                                                                 |
| ----------------------- | ------------------------ | ------------------------------------------------------------------------ |
| **成果页 / 总览页**(正) | 已完成、最该被记住的成果 | KPI 数字中染红"已落地"的那个;进度行里"已落地"用红、"推进中 / 规划中"用黑 |
| **问题页 / 现状页**(反) | **风险最高的那一个**痛点 | 多痛点并列时只给 1 个点红(红标题 / 左侧红竖条),其余中性灰                |

问题页判据：能造成**业务中断 / 单点故障 / 不可逆损失**的 > 仅影响效率的。只点前者。

**面积配额**（banner 外红色，按页面类型）：

| 页面类型                    | banner 外红色 | 做法                                                                     |
| --------------------------- | ------------- | ------------------------------------------------------------------------ |
| Cover / Closing             | ≤ 8%          | 模板自带全红 Cover 已足,不再叠加                                         |
| 标准正文页                  | ≤ 5%          | 1 个关键数字 + lead 竖线 + PDCA 图标(通用 / 项目模式不画底部红条)        |
| BEFORE / AFTER 对比页       | ≤ 5%          | AFTER 标题 + lead 竖线                                                   |
| 多 stat 并列页(3+ 个大数字) | ≤ 5%          | **只让 1 个用红,其余用 `#1A1A1A` 深灰** —— 大小造对比而非颜色            |
| 月报正文页                  | 豁免          | 底部红条为月报版式自带(见 §5 Page 3),各版式都有、不计入;正文区内仍按 ≤5% 人工把握 |

审核脚本按模式查配额（规则「红色面积超配额」）：通用 / 项目模式的每个正文页，把 banner 以外、填充色或描边色为品牌红 `#DB011C` 的形状按外框面积相加（直线按长 × 线宽），除以页面面积，超过 5% 就报；月报模式豁免、不查。局限：红色文字不计入面积（重点数字、AFTER 标题这类红字靠清单和人看）；图片里的红色（如 PDCA 图标）、表格单元格的底色也不计入；时间线类版式的状态色红描边按下面的例外不计入。

**禁区**：

- ❌ 用 `#DB011C` 作大段背景填充 —— 红色仅作锚点,不作背景
- ❌ Cover 自创深黑底 —— 模板 Cover 已是全红,不要再叠
- ❌ 三个大数字全部用红 / 问题页所有痛点全染红 —— 满屏告警 = 没有重点
- ❌ 没有理由的红色装饰条 / 红色边框 / 红色高亮框 —— 红色承担信息而非装饰
- ❌ 给 BEFORE 加红色 —— 红色锚点专属 AFTER

#### 例外：时间线状态色

时间线类版式（生成器的 `timeline`、`timeline-phase`，或手工做的时间线 / 阶段条）可以用状态色标出进度：

| 状态 | 颜色 | 形状区分 |
| --- | --- | --- |
| 已完成 | `#2E7D32` 深绿，上面的字 / 对勾白色 | 实心带对勾（阶段条：绿底白字） |
| 进行中 | `#F2A900` 琥珀，上面的字 `#1A1A1A` | 放大 + 外圈 +“当前”标签（阶段条：加高） |
| 未完成 | `#DB011C` 品牌红，只用空心或描边 | 白底红描边空心（阶段条：浅粉底 + 红描边） |

- 只用于时间线类版式，其他页面不用绿色和琥珀色。
- 状态必须同时靠形状区分（上表第三列），色弱和黑白打印也能分辨；配图例。
- 状态色（含未完成的红描边）不计入上面的面积配额；其他页的红色纪律不变。

### 6.4 三个高频组合（实战沉淀的视觉模式）

> 下面是手工排版的实战数值。生成器各版式的字号与间距是定稿值（如数据标签 16pt、说明 14pt、块间距 0.3″），以 `references/layouts.md` 为准。

整套 PPT 反复使用这三种组合,形成"重复"原则下的视觉特征:

1. **正文 lead 一致格式**
   红色锚点条 `#DB011C` (0.25" × 0.06") + 紧贴 16pt 加粗 `#1A1A1A` 文字。
   每页内容区起首必有,作为"故事开始"的视觉信号。

2. **大数字 stat callout**
   60–80pt 数字(`#DB011C` 或 `#1A1A1A`) + 红色短线 (0.5" × 0.04") + 14pt 加粗 `#1A1A1A` label + 11pt `#6B6B6B` 描述。

3. **icon row**(替代 4+ 个 bullet)
   圆形数字标号 (0.5" 红色或深灰) + 14pt 加粗 `#1A1A1A` 标题 + 11pt `#6B6B6B` 一句话描述。
   首项常用红圆吸引视线,其余用深灰圆。

## 7. 内容硬约束

### 每节一个核心信息

- 一节只回答一个问题，禁止多议题混搭
- 内容超出时拆成两节，不要塞满
- bullet list 是最后选择，能用大数字 / 对比 / 时间线 / 流程图就用

### 禁用元素

- ❌ **Emoji 占位符**(📷 📊 📈) —— 改用真实数据或简短文字
- ❌ **两栏 bullet list 堆砌** —— AI slop 标志
- ❌ **同一节 4+ 个 bullet 段落** —— 改用 card 网格 / 表格 / 图表
- ❌ **SmartArt 风格的方框+箭头流程** —— 改用极简数字标号 + 文字
- ❌ **空话套话开头**("在领导关怀下"、"经过不懈努力") —— 直接给结论
- ❌ **画饼词汇**("打造"、"赋能"、"未来可期"、"展望") —— 全部禁用

## 8. 常见失败模式与修复

| 症状                             | 原因                           | 修复                                            |
| -------------------------------- | ------------------------------ | ----------------------------------------------- |
| 第 06 节出现"将要 / 计划 / 未来" | 把 next step 混进了已完成节    | 把这些条目挪出去(除月报场景一律删除),保留已完成 |
| 第 08 节写了未来 roadmap         | 误以为"持续优化"=未来计划      | 改写为"上线后已经做过的迭代"                    |
| Agenda 缺了某节                  | 觉得不适用就跳过了             | 必须保留 8 节;本汇报无内容的节写"本期无更新"    |
| Agenda 顺序乱了                  | 按重要性排序                   | 严格按 §1 表格顺序                              |
| 主标题需要换行                   | 标题太长                       | 缩短到 ≤ 14 中文 / 28 英文;长内容移到副标题     |
| 副标题读不出故事                 | 副标题写成话题("关于项目背景") | 改成 action title:直接给结论                    |
| 副标题与正文 lead 完全相同       | 没做层级递进                   | 副标题写"短结论",正文 lead 写"结论+数据"        |
| 正文区铺满红色色块               | 误以为品牌色要"醒目"           | 按 §6.3 面积配额(正文页 ≤5%),红色仅作锚点       |
| 正文用色与红 banner 撞色         | 用了中明度蓝/绿/紫等冲突色     | 过 §6.2 撞色判断 3 问,改用色板内的色            |
| 出现渐变 / 阴影 / 发光           | 想做"高级感"                   | 全部去掉,Milwaukee 是工业 flat 风(§6.2)         |
| 一节信息塞不下                   | 多议题混搭                     | 拆成子节点(如 06.1 / 06.2),仍归属同一父节       |
| 没标 PDCA                        | 漏标                           | 在 banner 下沿与正文区上沿之间（1.02–1.30"）的右侧窄带加 PDCA 小图标(P/D/C/A,见 §2) |
| PDCA 写进了 banner 副标题里      | 位置错了                       | 挪到 banner 下沿与正文区上沿之间（1.02–1.30"）的右侧窄带的小图标位 |

---

## 9. 不要做的事

- 不要写"下一步"、"未来计划"、"Roadmap"(月报的"下一步计划"为唯一例外,且必须是已确定动作)
- 不要改 Agenda 8 节的顺序,不要删除任何一节(无内容也要保留并标注"本期无更新")
- 不要把 action title 放在主标题位置 —— 长结论会溢出,且不符合中文汇报体例
- 不要让副标题和正文 lead 完全相同
- 不要用目录式标题承担论证 —— "项目背景"只是话题,结论必须由副标题给出
- 不要写空话套话 / 画饼词汇
- 不要在同一节混多个议题
- 不要违反 §6 设计系统 —— 品牌锚点不可动;红色按纪律做"选择"(撞色、超配额、BEFORE 染红、渐变阴影等见 §6.2–6.3)
