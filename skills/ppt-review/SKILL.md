# 汇报 PPT 审核

milwaukee-ppt 生成 pptx 之后、交给人之前的一道**审核**：机械规则交给审核脚本，需要判断的交给下面的核对清单。所有修改都落在 **md 文稿**上，再重新生成；成稿 pptx 不手改（手改会在下次生成时被覆盖）。

下文 `<milwaukee-ppt>` 指 milwaukee-ppt skill 的目录（本仓库里是 `skills/milwaukee-ppt`）。

## 1. 审核循环

一**轮** = 跑脚本 → 过清单 → 改 md → 重新生成。最多两轮。

1. **跑脚本**（在文稿所在目录运行，md 里的图片相对路径才对得上）：

   ```bash
   python3 <milwaukee-ppt>/scripts/review_deck.py <文稿.md> <文稿.pptx>
   ```

   每条问题一行 `[规则] 位置：问题 → 怎么改`，全过只打印 `REVIEW OK`。退出码 1 表示文稿读不了或 pptx 打不开，按 stderr 修好再跑。规则全表见 `<milwaukee-ppt>/scripts/README.md`「审核命令」；生成时的 `警告:` 行也算本轮问题。
2. **过清单**：逐页、逐条过第 2 节，每条记"合格"或"不合格 + 改哪一层"。脚本已经报过的问题不在清单里重复判断。
3. **改 md**：脚本问题按它给的"怎么改"改；清单问题按该条写明的那一层改。改动碰到简报时按第 3 节处理。
4. **重新生成**，覆盖同一个 pptx：

   ```bash
   python3 <milwaukee-ppt>/scripts/generate_ppt.py <文稿.md> -o <文稿.pptx>
   ```

   退出码非 0 是改出了文稿错误，按错误信息里的「页「标题」」修好再生成。

本轮脚本 `REVIEW OK`、清单全合格、没有生成警告，就直接交付。否则进入下一轮。第二轮改完、重新生成后，再跑一次脚本、过一次清单，这次只记录结果、不再改，作为**最后一轮结果**交付。

**可选：转 PNG 看图**（Claude Code 里能读图时用；规则不依赖它）：

```bash
soffice --headless --convert-to pdf --outdir <目录> <文稿.pptx>
pdftoppm -png -r 80 <目录>/<文稿.pdf> <目录>/page
```

逐页看脚本看不出的观感：留白是否失衡、视觉重点是否落在 `!` 标的那一项。看到的问题仍归到清单某一条、按那条的层去改。

## 2. 核对清单

只收脚本算不出、要靠判断的项。每条：看什么 → 不合格时改 md 的哪一层。层有五种：**版式**（`Layout:`）、**内容量**（条目增删、拆页合页）、**页序**（`#` 页的先后）、**标题**（`##` action title、红条结论行）、**`!` 标记**。

| # | 看什么 | 不合格时改 |
| --- | --- | --- |
| 1 | **一页一个核心信息**（milwaukee-ppt §7）：这页每个条目、数字、图都在支撑本页 `##` 那句结论。有条目在讲另一件事就不合格。 | 内容量：挪到它该在的页，或拆成新页（项目汇报模式下拆成同一节的子节点页） |
| 2 | **版式和内容的形状相符**：内容本身是步骤、数字、前后对比、时间节点、对象×维度中的哪一种，版式就该是对应那种（依据 `<milwaukee-ppt>/references/layouts.md`「选版速查」）。有先后的事写成要点列表、并列对象的多维比较写成要点、结果数字埋在句子里，都不合格。 | 版式：换成相符的版式，字段按新版式的写法重写 |
| 3 | **每页的量**（亲密性、§7）：每条说明是一句话，不是一段；同一页的条目在同一个粒度上；整页能一眼分出的视觉块不超过 5 组。 | 内容量：删到一句话、合并同类项；删完仍多就拆页 |
| 4 | **副标题串成故事**（§4 验收）：按页序只读所有 `##`，能读出"问题 → 做了什么 → 结果 → 结论"的一条线；读到某页断了、跳了或重复了就不合格。 | 标题：改那页 `##` 的措辞；是顺序不对时改页序 |
| 5 | **相关的页挨着**（亲密性用在页与页之间）：讲同一件事的页相邻，结论页在它的支撑页之后紧跟着。项目汇报模式的八节顺序脚本已查，这里只看节内和非项目模式的顺序。 | 页序 |
| 6 | **`!` 标在对的那一个**（§6.3 红色纪律）：成果页的 `!` 给已落地、最该被记住的那个结果；问题页给风险最高（会造成业务中断、单点故障、不可逆损失）的那一个；timeline 的 `!` 只给真正的关键里程碑。没有明确的"第一"时一个都不标。 | `!` 标记：挪到对的条目，或去掉 |
| 7 | **对比要截然不同**（对比原则）：before-after 两侧讲同一件事、同一维度，差别一眼可见；stats 页几个数字里重点那个和其余的区别靠 `!` 而不是靠措辞。前后差别只是换了说法就不合格。 | 内容量：两侧改成同一维度的可见差别；做不到就换版式（如 table 或 stats） |
| 8 | **全篇写法一致**（重复原则）：同类条目用同一种写法（标签都是名词短语、说明都是一句结论），同类内容用同一版式，口径行写法一致。 | 内容量：统一字段写法；同类内容统一版式 |
| 9 | **已落地 vs 未来**（只在 `report: project` 时查，§3）：06 OUTCOMES、08 LESSONS 节里的动词都是已完成态；整篇没有 `Next:`、"将要 / 计划做 / 下一步 / roadmap"。"按计划上线"这类讲已发生事实的说法合格。 | 内容量：删掉未来的条目和 `Next:`，或改写成已经做过的事 |
| 10 | **和简报一致**（有定稿简报时）：页数、页序、主标题、结论标题、数字与简报逐项一致。 | 按第 3 节处理 |

## 3. 改动和简报冲突时

用户用 ppt-grill 定过**简报**（文稿目录下的 `简报.md`）时，简报是用户确认过的，审核的改动分两类：

- **可以改，同步简报**：换版式、拆页 / 合页、调页序、改 `##` 措辞、挪 `!`。先改简报对应行，再改 md；交付时在"简报改动"里逐条列出。
- **不改，列为未解决项**：核心结论、观众、任何数字和它的口径、删掉简报里有的页。这些是用户的决定，写清问题和建议，交人决定。

没有简报时，第二类改动同样不做，直接列为未解决项。

## 4. 交付给人

把下面几项一次贴给用户：

1. **成稿**：md 文稿和 pptx 的路径。
2. **最后一轮结果**：脚本输出原文（含末行 `REVIEW OK` 或 `REVIEW: N 条问题`），加清单里不合格的条目（页 + 条目号 + 问题）。
3. **改了什么**：每轮一段，列改动的页和层。
4. **简报改动**：有简报时逐条列；没有改动写"无"。
5. **未解决项**：每项写页、问题、为什么没改（两轮用完 / 要用户决定 / md 表达不了、要在成稿上手工细调或改生成器），以及建议怎么处理。

人审核时还要改某页细节，回 milwaukee-ppt「生成后细调」。
